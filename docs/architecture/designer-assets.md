# Designer Image Assets
PXA stores customer images as organization-owned objects instead of embedding their bytes in template or workbook JSON. PDF and Spreadsheet Designer use the same authenticated asset API and storage boundary.

## Storage model

- Binary content is written through `IPxaObjectStorage`. The development and default On-Premise adapter writes below `PXA.WebApi/App_Data/objects`; the path is configurable through `Storage:RootPath`.
- PostgreSQL table `administration.stored_objects` contains only the opaque object key, organization and creator IDs, purpose, media type, original file name, byte length, SHA-256 checksum, lifecycle status, and timestamps.
- Template and workbook JSON contain an opaque `assetId` and a same-origin content URL. They do not contain the uploaded image bytes.
- Object keys are generated by the server and never contain customer file names.

The local filesystem path is an implementation detail. Cloud and clustered installations must provide shared object storage through the same abstraction rather than mounting local container storage.

## API

All routes require an authenticated Designer session, an active organization, CSRF protection for mutations, and the effective Designer entitlement.

| Operation | Route | Result |
| --- | --- | --- |
| Upload | `POST /api/pxa/v1/designer/assets` | Stores a multipart `file` and returns metadata plus `contentUrl`. |
| Metadata | `GET /api/pxa/v1/designer/assets/{id}` | Returns metadata for an asset in the active organization. |
| Content | `GET /api/pxa/v1/designer/assets/{id}/content` | Streams private content with ETag and range support. |
| Delete | `DELETE /api/pxa/v1/designer/assets/{id}` | Soft-deletes metadata after deleting its object content. |

Cross-organization IDs return `404`, so asset existence is not disclosed.

## Image rules

- Accepted formats: valid PNG and JPEG files.
- Default maximum upload size: 10 MiB (`Storage:MaximumDesignerAssetBytes`).
- Maximum decoded dimensions: 100 million pixels.
- The server derives the media type from decoded content; it does not trust the extension or multipart media type.
- Invalid, empty, unsupported, oversized, and malformed images are rejected before storage.

## PDF Designer

Uploading or dropping an image stores it once and writes `assetId` plus the private content URL to the image element. Existing templates with a `data:` URL or external source URL remain readable. Export resolves authenticated asset content immediately before sending the transient render request; persisted template JSON continues to hold only the reference.

## Spreadsheet Designer

Worksheet `images` entries contain an `assetId`, cell anchor (`row`, `col`), dimensions, file metadata, and alt text. The selected-cell Image action uploads through the common asset API. Images move with inserted rows or columns and are removed from the sheet model when their anchored row or column is deleted.

XLSX import extracts supported drawings and immediately uploads them to the organization asset store. XLSX export resolves referenced assets only for the duration of the request and embeds them in the generated workbook. The transient `data` field is an import/export transport detail and must not be persisted.

## Lifecycle and operations

The Designer does not automatically delete an object when an element is removed because one asset may be referenced by multiple drafts or versions. Explicit deletion is available through the API. Reference tracking, retention policy, and orphan cleanup remain required before exposing a general asset-library delete workflow.

Storage reconciliation detects database records whose object content is missing. Backups must include PostgreSQL and object storage from the same recovery point. Logs and telemetry must never contain image bytes, signed URLs, or customer file names.
