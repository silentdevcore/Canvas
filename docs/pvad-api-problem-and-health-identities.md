# API Problem And Runtime Identity Migration

Canonical API routes now write PVAD problem-type URLs and browser trace names.
Health-check registrations and the Npgsql telemetry datasource name also use PVAD.
This changes emitted identifiers, not diagnostic decisions, authentication or the
physical PostgreSQL database. Coordinate exact-match integrations before rollout.

## Problem Details

For responses generated by `PvadApiProblems` on `/api/pvad/...`:

```json
{
  "type": "https://docs.pvade.com/problems/pvadapi006",
  "status": 409,
  "code": "PXAAPI006",
  "canonicalCode": "PVADAPI006",
  "canonicalType": "https://docs.pvade.com/problems/pvadapi006",
  "legacyType": "https://docs.powerdoxautomation.com/problems/pxaapi006"
}
```

The authoritative `code` and its numeric meaning do not change. The canonical
type path uses the bounded diagnostic alias where one exists; unknown diagnostic
IDs keep their own suffix, escaped as a single URI path segment. This is not a
general diagnostic prefix rewrite. Titles, status, detail, trace and instance
handling retain their existing rules.

Old branded routes rewritten by `PvadLegacyApiMiddleware` keep the original type
URL. Neutral legacy `/api/...` routes outside the `/api/pvad` segment do likewise.
They add the same canonical/legacy references. The middleware marks a rewritten
request internally, so its original identity is not lost when its path changes.
Clients cannot select this marker through a header; authorization is unchanged.

Shared completion never overwrites an explicitly supplied `type`. For recognized
generated type URLs it adds both references; for custom or framework types it
does not invent aliases and removes stale generated reference fields. Historical
responses, audit evidence and job records are not rewritten.

Designer template conflicts use the canonical type
`https://docs.pvade.com/problems/designer-template-conflict`. Their old root-domain
type remains available on legacy routes and in `legacyType`. Existing revision,
updater and conflict diagnostics are unchanged.

Problem-type URIs are identifiers. Source tests do not establish DNS/TLS readiness,
remote redirects or dereferenceable documentation pages for these URLs. Consumers
should migrate exact URI matchers, prefer stable codes for decisions and tolerate
unknown extension fields.

## Health And Persistence Telemetry

| Producer or consumer | Canonical value | Retained behavior |
| --- | --- | --- |
| Database readiness registration | `pvad-database` | System health can read `pxa-database` when canonical registration is absent |
| Mail readiness registration | `pvad-mail` | System health can read `pxa-mail` when canonical registration is absent |
| Npgsql telemetry datasource name | `pvad-database` | The old name remains an explicit compatibility constant, not a second pool |

Canonical registrations are authoritative if both names are present. Missing
registrations fail unhealthy. The Admin response component keys (`database`,
`mail`, etc.) and sanitized summaries stay stable. Publisher metrics use the
registered names; update any external exact-match dependency-name queries.

The datasource name is instrumentation metadata, not the database name, role,
connection-string key, EF migration history or a storage location. None of those
physical/persisted identities is migrated by this change. No duplicate health
registration, database connection or metric emission is introduced for aliases.

## Browser Traces

New spans use `pvad.browser.application`, `pvad.browser.version` and
`pvad.browser.event_count`. Correlation events use `pvad.browser.status.correlation`
and `pvad.browser.source_correlation_id`. Existing validation, bounded payloads,
route normalization and privacy rules stay in place; rejected batches write no
new trace attributes or events.

Stored old trace keys are not rewritten. Update custom Tempo searches and trace
processors to handle old and new attributes during retention overlap. The new
writer does not dual-emit events or duplicate measurements. Browser request DTOs,
API paths and canonical metric names do not change.

## Validation And Rollout Limits

Unit tests exercise canonical/legacy error types through the actual rewrite
middleware, custom types, stable codes, health-name fallback and precedence,
sanitized health summaries, valid trace output and rejection before trace writes.
Configuration contracts tie registration and writers to their shared constants.
These isolated tests do not start the full Identity/API host or PostgreSQL.

Deploy matched producers, readers and custom-query updates together. The existing
API integration, deployed-host and backup/rollback gates remain separate. No
production database, trace history, secret or remote configuration is changed by
the source migration.
